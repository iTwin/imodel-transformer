# Automatic bulk element reservations: implementation spec

Status: automatic TS-only reservation handling is implemented across the processing entry points, including deferred provenance, ordinary insertion, callback metadata, deletion fallback, and finalization boundaries. Public-entry-point acceptance fixtures, learning documentation, a major change file, and generated error API entries are present. Implementation and subsequent simplification validation are recorded below. The accepted design and deferred upstream questions are recorded in Obsidian at `iModel Transformations/ADRs/0001-automatic-bulk-element-reservations.md`.

## Outcome and completion check

For supported SchemaSync reservation workflows, each outermost transformer processing call discovers its target inserts, reserves them in bulk, and only then modifies elements. A parent plus 24 new coded children must use one reservation API call and ordinary insertion must assign all reserved IDs. Existing matches produce no reservation requests. Incremental source updates that become target inserts do produce requests.

Completion requires the acceptance matrix below, transformer build/test/coverage, regenerated API reports where needed, release notes, and linked learning documentation. Local tests are the merge gate. Cloud locking, uploads, competing briefcases, and service performance are explicitly not established by local tests.

## Accepted constraints

- First iteration stays in transformer TypeScript and uses the installed backend/native APIs unchanged. No core/native implementation work or dependency changes. Record upstream constraints and possible improvements in the ADR for later review; they are not prerequisites for this iteration. This decision does not silently exclude new-model transfers or approve bypassing transform customization.
- Automatic handling in relevant reservation-enabled targets; no new opt-in flag, SchemaSync enablement, lock-policy change, or fake compatibility API.
- Each outermost existing processing call is a preparation/reservation/execution unit. Nested dependency discovery belongs to that unit. Two caller-issued subset calls are two units. No new caller preparation/grouping API or public/protected preparation override.
- Preserve existing non-reservation behavior and existing subset finalization semantics. Do not turn each subset call into a save/finalize operation.
- Resolve target matches before building the reservation set. Preserve mapping/GUID/code match precedence, code class checks, and whitespace handling.
- Reserve target inserts, not source changeset insert IDs. Updates and deletes wait for the reservation stage but are not reserved.
- All batches must succeed before the operation's element modifications. Reject cases requiring an element insert before later reservations can be prepared. Do not introduce a reserve/insert/reserve loop.
- Prefer one call. Multiple bulk batches are allowed only for an actual dependency requirement, not speculative chunking. Never retry or fall back to singleton requests after failure.
- Upfront preparation may use extra memory and delay insertion. Do not retain geometry payloads across the whole operation merely to defer insertion.
- Use `targetDb.reservations.reserveElements({ elements })` with target `classFullName`, federation GUID, and code. Backend assigns the ID during ordinary insertion. Never manufacture target IDs, install placeholder native context mappings, or set `forceUseId` to consume a reservation.
- Reservation and insertion use the same code scope representation. GUID and numeric scopes are not interchangeable for reservation equality even if they identify the same element.
- Unsupported reservation combinations fail before element modifications. In particular, do not silently replace preserve-ID or in-place/template identity semantics.
- The caller must ensure that a shared reserved identity represents identical contents across briefcases, including custom transformations. Document this requirement; do not add a full-content comparison or claim that backend class/code checks establish it.
- Preserve original backend errors. Log reservation failures once at the reservation boundary with phase, batch size, and available error details; rethrow the same object. No whole-operation reservation rollback claim.
- Successful reservations can outlive insertion failure. Do not abandon or save caller-owned transactions automatically beyond existing documented workflow behavior.

## Execution architecture

### 1. Private outer-operation boundary

Add one package-private operation implementation in `packages/transformer/src/ElementReservationOperation.ts`, owned by `IModelTransformer`; do not export it from the package entry point. Integrate through private transformer methods, not a supported public/protected preparation callback. Scope operation state with `try/finally` and a nesting counter so nested processing joins the current operation.

Use the reservation path when `targetDb.reservations.isServerBased` is true and `targetDb.holdsSchemaLock` is false. Otherwise execute the existing path directly. The backend bypasses reservation enforcement while the schema lock is held; do not add reservation work to that bypass. Never use `skipReservationCheck` to implement this feature.

Enter the boundary before implicit `initialize()`, not after it. Cover `process`, `processElement`, `processChildElements`, `processModel`, `processModelContents`, `processSubject`, and `processRelationships`. Schema/code-spec/font-only entry points remain setup operations. Keep existing root-subject validation. Do not call `reserveElements` for an empty request set.

Split `processAll` and `processChanges` into their existing export portion and post-import tail. Discovery must not run reference repair, geometry optimization, project-extents updates, synchronization version updates, finalize, or the incremental save callback. Those run only after replay succeeds. Subset methods still require caller finalization and saving.

### 2. Collect one ordered operation, without element writes

Temporarily register an internal `IModelExportHandler` adapter on the existing exporter and restore the transformer handler in `finally`. Keep the existing exporter instance, exclusions, change data, and traversal implementation. Do not run a second export pass or create a fake importer whose inserts pretend to have succeeded.

The adapter delegates selection callbacks with the count/order of one normal exporter traversal and journals accepted execution events: elements, models, aspect cleanup/owner groups, unique/multi-aspects, relationships, and deletions. Store source IDs and small event metadata; hydrate source entities during execution. Keep multi-aspect grouping and skip/cleanup notifications in their existing order. Never invoke a mutation-capable export/import callback during collection. Progress callbacks must not imply that target imports have already completed.

Preparation uses the existing required-reference discovery rules, augmented with operation-local states `visiting`, `prepared`, and `existing`. Keep model scheduling separate from modeled-element identity. A prepared element has a logical identity, not an `Id64`; a model is not considered present merely because its modeled element is scheduled. Detect required dependency cycles before reservation. Optional references may continue through existing post-import repair if they do not determine reservation identity.

The journal must preserve model-before-contents execution and owner-before-aspects execution. New models are not automatically out of scope: their reservation tuples may be preparable without their final model IDs. Gate G1 must establish a TS-only identity-preparation path against real source elements and ordinary native cloning/insertion during replay. Full native cloning before the target model exists is not itself a requirement. If the TS path cannot determine an identity without prior target writes, identify the exact unsupported case instead of introducing placeholder IDs or quietly dropping normal model transfers from scope.

`initialize()` currently calls `initScopeProvenance()`, which inserts or migrates an aspect. In `ProvenanceManager.ts`, separate scope lookup/validation and in-memory version preparation from persistence. During an active operation, queue the resulting scope insert/update and persist it after reservation success, before replay needs its real aspect ID. Existing explicit `initialize()` calls outside an operation retain their existing behavior; their earlier writes are not retroactively part of a later reservation gate. Test both initialization paths and synchronization-version caching.

Schema, code-spec, and font/resource setup may retain their existing prerequisite writes. The guarantee is not that the entire target database is untouched on failure: it is that this operation's transformer-owned element/model/aspect/relationship/provenance modifications and finalization have not started. Arbitrary caller code writing directly to a database is outside that guarantee.

### 3. Prepare target identities and exact request codes

Extract the existing target matching decision from `onExportElement` into a private helper shared by preparation and the ordinary path. Retain mapping first, source federation GUID second, and transformed-code matching third, including the same-class check and clearing a conflicting-class code. Do not normalize/truncate code values or replace whitespace-preserving SQL with `Code` construction for target lookup.

Track each accepted source element by source ID with its existing target ID or pending insert identity, its transformed class/GUID/code tuple, and any logical code-scope dependency. Record genuine existing matches in the normal clone context as today; never record a pending insert as a real target mapping. Distinguish genuine empty codes from codes lost through unresolved mappings. Reject unresolved nonempty code identities rather than reserving an accidental empty code.

For an existing scope, use its actual target ID for code lookup and reservation. For a new prepared scope, use that scope element's prepared target federation GUID, not an unconditional copy of its source GUID. A scope matched to an existing target with a different GUID uses the target identity. If a new scope has no usable GUID, a dependent coded insert cannot be prepared without inserting the scope first: reject that graph before reservation and element writes. An uncoded insert without a GUID remains an ordinary backend insert and is not reserved; it still waits behind the operation gate.

`IModelCloneContext.prepareElementIdentity` scopes the mapped code before the empty-code fallback and `onCloned`. The standard clone path imports/maps CodeSpecs lazily, as native cloning does; incremental exports need not include unchanged CodeSpecs. It reads raw stored code props, not `Element.code`, because the latter trims whitespace even when the database stores exact code values. The intrinsic empty code needs no native code-spec mapping; empty-valued domain codes retain their mapped spec. Preparation retains both the final reservation identity and `codeBeforeHooks`. `transformPreparedElement` pins that original code input during ordinary replay and checks the final GUID/class/code against the prepared identity. Replaying with the final customized code as the input would apply customization twice. GUID/numeric scope representation stays pinned; undefined and empty code values follow the existing empty-value equivalence. Scoped state is restored in `finally`. The earlier constructor callback prototype has been removed.

When the source model has no existing target model mapping, preparation supplies a guarded TS identity view instead of requesting a full native clone. Explicit class remappings are mirrored for that view. Existing `onCloned` and `onTransformElement` callbacks still run and may change its identity fields using source data. The base transform defers its non-identity adjustments to replay. Reads or enumeration of unavailable target props fail with `ElementReservationUnsupported`, rather than returning fabricated values or silently omitting callbacks. This also means a class hook requiring full target props is unsupported in this situation, even if it is ultimately identity-neutral. When the real target model is already available, preparation uses ordinary native cloning. This is not a proof of arbitrary callback purity; context-dependent identity changes during execution are still rejected by the replay guard. No supported preparation hook or placeholder native mapping is introduced.

Retain only identity metadata, not full geometry payloads. Rehydration/re-transformation during replay is permitted by the existing side-effect-free/multiple-call contract, but that contract alone does not prove hooks can run before target dependencies exist. Do not add a second evaluation of selection filters during replay; retain the evaluations performed by the single original traversal, including any existing hierarchy checks. Preparation-time transform hooks must not require prior target element writes. Source and caller-owned target state must remain stable for the duration of the processing call.

Deduplicate repeated visits by source ID. If distinct prepared source elements collapse onto the same new GUID or nonempty code before either exists in target, reject the ambiguous merge as unsupported before mutations; do not silently reserve two identities or invent a provisional target ID. Existing real target matches remain supported.

### 4. Validate and reserve

After discovery completes, validate all prepared identities and all required code-scope dependencies. Check known unsupported mode combinations only when they would require reserved inserts. Preserve-ID filtering, template/in-place cloning, and copied-target paths must not be changed into shared-ID allocation paths. Existing-match-only operations remain valid where their current semantics permit them.

The first implementation submits one nonempty array to `targetDb.reservations.reserveElements`. Do not query `needsElementReservation` per candidate to eliminate existing reservations; including an existing identical reservation in the batch provides real class/code validation and reuse. Missing GUIDs are omitted from the request set, not synthesized. Malformed explicitly supplied GUIDs and backend class/code validation failures retain the backend error contract.

Wrap only the awaited batch call in its logging/rethrow boundary. Use the transformer logger category with metadata `{ phase: "reserve-elements", batchSize, error }`. Do not log the same failure again in outer wrappers. Backend allocation/storage rollback is backend-owned; transformer does not delete reservations or touch the SchemaSync counter.

### 5. Replay without changing the reserved identity

After successful reservation, restore the original handler and replay the journal in order, invoking existing execution callbacks once. Resolve actual target IDs through ordinary importer insertion and then update the clone context as today. New model events use the inserted modeled-element ID and precede contained element insertion. Run aspect cleanup only when its real target owner mapping exists.

Use the prepared match decision during reserved-path execution rather than doing a fresh, potentially divergent GUID/code match after earlier writes. Re-transform props with the pinned code resolver active. Before importing each planned insert, verify its class, federation GUID, code spec/value, and scope representation still match the prepared tuple. The importer must continue seeing `id: undefined` for that insert. A mismatch fails; never overwrite arbitrary transformed identity fields to force a match.

A known unsupported mode or unresolved identity is rejected during preparation. A custom hook that changes its identity later, introduces an unplanned insert, or otherwise violates the preparation contract is an execution-time contract failure. It can occur after earlier replay writes, just like any insertion failure; this plan does not promise to prove arbitrary callback behavior or roll back caller transactions. Tests and documentation must distinguish those cases. Do not add a speculative hook-purity or full-content detector. The documented identical-content guarantee remains the caller's responsibility.

Add a private importer integration guard for planned reserved inserts if needed to check the props immediately before ordinary insertion. It must not reserve, allocate IDs, replace native insertion, or become a new public/protected override. Direct use of `IModelImporter` without `IModelTransformer` is outside automatic preparation; its caller remains responsible for backend reservations.

Release journal/temporary scope state in `finally`. Never let pending logical identities leak into later calls as real mappings. Preserve existing actual mappings and transaction ownership. Tests must establish clean reuse after preparation/reservation failure; after an execution failure and caller rollback, require a fresh transformer unless existing context restoration is explicitly proven.

### 6. Error ownership

Add `IModelTransformerError.ElementReservationUnsupported = "element-reservation-unsupported"` for known unsupported preparation/mode/ambiguous-identity cases, and `ElementReservationPlanChanged = "element-reservation-plan-changed"` for execution-time identity drift or an unplanned reserved insert. Throw these with `ITwinError` and `IModelTransformerErrorScope`; include the source ID and actionable reason without claiming full-content validation. Missing ordinary source references retain the existing dangling-reference policy. Unexpected internal journal/mapping inconsistencies remain plain errors/assertions.

Do not translate backend reservation conflicts, invalid-reservation errors, class/code errors, or native insert failures into these keys. If a deliberate translation of another error becomes necessary, preserve its cause and document that decision; do not add a catch-all translation.

### 7. Feasibility review resolution

A read-only architecture review identified real risks in handler side effects, model identities, aspect cleanup, native code clearing, and replay-time transformation. This spec addresses them with a single selection pass, logical identities outside native maps, deferred data/provenance writes, pinned code representation, and the G1 TS identity-preparation gate. It does not adopt a blanket ban on custom transformations or claim a preflight can prove their purity; those would contradict the accepted documented caller contract. Do not weaken the pre-reservation mutation gate to make a fixture pass.

### First G1 attempt: full-clone-first preparation is blocked

Executed `pnpm --dir packages/transformer exec vitest run src/test/standalone/ElementReservations.test.ts` against core 5.13.0/native 5.13.28. Preparing the real source parent and 24 children succeeds using an internal constructor-supplied code resolver while all target mappings remain absent. The test then submits one real reservation batch, re-clones parent-first, and verifies ordinary insertion assigns all 25 reserved IDs and persists numeric parent code scopes. However, preparing a `PhysicalObject` before its source model has a target mapping throws `Invalid target model` inside the native `cloneElement` call. The code-resolver callback has not run at that point.

The control case inserts a real target `PhysicalModel`, maps the source modeled element to it, and repeats the same clone. Cloning then succeeds and invokes the code resolver. No fabricated target IDs are used. This establishes that the proposed JavaScript code-scope seam alone cannot support the required new-model case. It does not establish whether native cloning would accept a valid-looking ID for a nonexistent model; introducing such an ID would violate the agreed no-placeholder constraint.

At the end of the first attempt, the retained test asserted this backend limitation and its control case; its green result did not mean the feature gate passed. ### G2/G3 implementation result

`ElementReservationOperation.ts` owns the typed ID/metadata journal and single reservation call. `ElementReservationState.ts` supplies package-private exporter/importer state without a supported preparation extension. The importer guard runs at ordinary insertion and remains active through post-replay/save work. New Categories own native creation of their default SubCategories; the default is mapped and updated during execution rather than separately requested or inserted.

Incremental callbacks retain the actual `ChangedInstanceIds` while replaying, even though `exportChanges()` has cleared its private traversal state. Model deletion can append a partition to the deferred element-deletion boundary; an empty boundary is inserted after model deletions when discovery did not have element deletes. Tests cover real populated-definition-model fallback and consecutive processing calls. Full processing retains element/aspect repair before relationships; incremental processing retains its original relationship-before-post-export-repair order. A review suggestion to change incremental ordering was rejected after comparison with the original `processChanges` implementation.

Preparation/reservation failure restores implicit initialization and deferred scope/cache state. Tests cover new scope insertion, legacy scope migration, cached synchronization versions, failed reservation followed by reuse, and original backend errors. Code-conflict clearing validates the hook's pre-matching code before applying the recorded rewrite, so it cannot conceal later drift. CodeSpec mapping is initialized lazily only when the standard clone path needs it.

Superseded: native 5.15.14 fixed this ([imodel-native#1640](https://github.com/iTwin/imodel-native/issues/1640)), the transformer now requires iTwin.js 5.15, and `ElementIdSet.ts` was removed. The original note follows. A real native 5.13.28 limitation surfaced with reserved IDs such as `0xfffff60000000001`: they pass `Id64.isValidId64` and ordinary bound equality, but `IdSet` rejects them. `InVirtualSet` accepts the same compressed binding. `ElementIdSet.ts` therefore preserves `IdSet` for ordinary IDs and supplies a bound existing-element subquery for SchemaSync-reserved IDs. Target aspect cleanup/deletion and source hierarchy/aspect/change-expansion queries use this path.
