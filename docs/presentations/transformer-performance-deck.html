~70 seconds. The same suite protected us in two ways. First, it exposed an update-heavy changeset-scanning regression: the candidate was more than three times slower and used more memory. PR #342 is the main related Transformer change, but the candidate also upgraded Core, so the result identifies the path to investigate without assigning the full regression to one PR. Second, the suite disproved the bulk-element-loading experiment in PR #392. It sounded promising because it reduced round trips, but serialization made it two to two-and-a-half times slower. We closed that direction before adding complexity. Meanwhile, balanced synchronization and schema processing stayed within our five-percent signal threshold.

How we moved quickly

A/B testing turns an idea into evidence

Step 1

Build a focused model

Generate exactly the data shape that exposes the suspected bottleneck.

Step 2

Build both branches

Prepare baseline and candidate from known revisions.

Step 3

Use one runner

Both versions execute on the same GitHub Actions machine.

Step 4

Alternate samples

Run baseline and candidate repeatedly in isolated processes.

Step 5

Compare medians

Use 40 measured samples per arm so outliers do not drive the story.

iT Same machine · alternating order · repeatable fixtures
6
~60 seconds. Every quick test begins with generated data tailored to a question. The workflow builds both revisions, then runs them on the same machine. Baseline and candidate samples alternate, each in an isolated process, reducing machine drift and cross-test contamination. We take the median of 40 measured samples per branch—not a single run and not a simple average that can be distorted by an outlier.
Why the quick suite works

Fast, controlled, and intentionally focused

Strengths
  • 1Minutes, not hours: small targeted fixtures make iteration practical during development.
  • 2Precise control: generate delete-heavy, relationship-heavy, or large-base/tiny-change data on demand.
  • 3Reproducible comparisons: the fixture recipe and branch revisions are captured with the result.
Tradeoffs
  • 1Synthetic data is small: it may not reproduce every real-world model characteristic.
  • 2Focused tests amplify one shape: a 60% delete-heavy win is not a 60% promise everywhere.
  • 3Thresholds are signals: important decisions still deserve repetition and real-model validation.
iT Quick suite for iteration; comprehensive suite for broader confidence
7
~55 seconds. The old performance suites are comprehensive but can take hours because they use large models and many cases. This suite trades breadth for speed and control. Generated fixtures let us amplify one behavior and iterate quickly. The tradeoff is realism: synthetic models are smaller and cleaner than customer data. We use the quick suite to learn and screen ideas, then use broader testing when the decision requires it.
